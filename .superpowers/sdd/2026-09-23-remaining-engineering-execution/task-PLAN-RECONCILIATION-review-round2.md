2. **The register still tells the D4 implementer to use a client-IP source that the accepted trust decision forbids.** `docs/REMAINING_ENGINEERING_PLAN.md:383-387` prescribes `request.ip`, calling it valid because `trustProxy` is enabled. The same register's P0-4 row at `:233` explicitly calls `trustProxy: true` independently spoofable, and its D4 progress row at `:324` names the private `X-OKR-Client-IP` signal and peer fallback. The accepted ADR forbids `X-Forwarded-For`/`X-Real-IP` as control keys (`docs/client-ip-trust-adr.md:53-54`) and permits a throughput limiter to fall back only to the peer (`:58-63`). The real SPA relay forwards the private header and omits public forwarding headers (`spa-web/src/lib/bff-proxy.ts:88-103`), while Fastify still uses `trustProxy: true` (`spa-bff/src/server.ts:243`). Therefore `request.ip` can collapse ordinary SPA traffic into the SPA peer bucket; an exposed path accepting forwarding headers can instead make the key caller-selected. T33 correctly tests the private-header relay, but T24 (`execution plan:72`) and the fixed D4 assumption (`:210`) say only IP-keyed and do not resolve this contradictory source. Correct the stale canonical instruction and explicitly require T24 to derive the key from the trusted private header, falling back to the raw transport peer for throughput limiting, never `request.ip` as a trusted-proxy interpretation or XFF/X-Real-IP. Include private-header separation, missing-header aggregate fallback, and ignored forwarding-header behavioral cases.
